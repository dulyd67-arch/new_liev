# نتيجة تحقق المرحلة الأولى

التاريخ: 2026-11-07. البيئة: Node.js 24.22.1، npm 11.9.0، Python 3.12،
Docker 29.9.2، وPostgreSQL 17 داخل Docker.

يسجل هذا التقرير نتائج قبول أساس المرحلة الأولى قبل إضافات المرحلة الثانية؛
اختبارات المصادقة وإدارة المستخدمين ستوثق مع قبول مرحلتها.

**اجتاز أساس المرحلة الأولى قبول المعمارية وقاعدة البيانات وAPI.**
نجحت الترحيلات والبناء واختبارات الخادم وقاعدة البيانات ومطابقة المخطط
والتعافي من تعطل Redis. بدأ تنفيذ المرحلة الثانية بعد قبول هذا الأساس؛
المصادقة اجتازت لاحقًا قبول المرحلة الثانية الموثق في
[سجلها المستقل](PHASE2-VALIDATION.md).

تحزيم API كصورة Docker وتشغيل الصورة لم يثبتا بعد. تعطلت المحاولة الأولى
بسبب حد مساحة بيئة البناء، وعولج ضغط المساحة محليًا لاحقًا لإعادة المحاولة.
هذا قيد تشغيل مسجل ضمن أعمال النشر والمرحلة الثامنة، ولا يغيّر نتائج تشغيل
الخادم المبني على المضيف وقاعدة البيانات المثبتة أدناه. لا يوجد نشر إنتاجي
أو مزود دفع مربوط أو أموال حقيقية، والمنصة الكاملة غير مكتملة.

فحوص المخطط تغطي 35 جدولًا و14 enum و55 مفتاحًا أجنبيًا و89 فهرسًا
في الترحيل الأولي. تضيف الترحيلات المالية فهارس وقيودًا وtriggers أخرى.
الترحيل الأولي أُنتج أولًا بأداة Python محدودة ومرفقة عندما لم تكن الشبكة
متاحة. تم لاحقًا التحقق من صلاحية المخطط بالـCLI الحقيقي وتطبيق الترحيل
بنجاح على PostgreSQL. أكّد فحص diff عبر Prisma عدم وجود اختلاف بنيوي يكتشفه
بين المخطط وقاعدة البيانات؛ قواعد CHECK وtriggers اليدوية تختبر باختبارات التكامل.

## قيد صورة Docker وما بقي للتحقق

- فشلت محاولات إنهاء/تصدير صورة API بخطأ `no space left on device` في مخزن
  Docker الذي يستخدم VFS ضمن مساحة بيئة تبلغ نحو 8 GB. نجحت أوامر تثبيت
  الحزم وتوليد Prisma وبناء TypeScript داخل محاولة Alpine قبل فشل إنهاء الصورة.
- عولج ضغط المساحة لاحقًا بتسطيح طبقات rootfs المحلية الخاصة بـPostgreSQL،
  مع إبقاء ملفات PostgreSQL 17 الرسمية وvolume البيانات دون تغيير، وتحرير
  نحو 3.8 GB. هذا إجراء في بيئة الاختبار المحلية فقط؛ يظل Compose في المصدر
  يشير إلى الصور الرسمية، ولا يمثل ذلك تغييرًا في إعداد إنتاجي.
- ما زال يلزم
  إكمال الصورة وتشغيلها وفحص الترحيلات والجاهزية داخلها على بيئة ذات مساحة
  كافية. لا تتضمن النتائج أعلاه ادعاءً بأن صورة API النهائية قابلة للتشغيل.
- لم تُشغّل اختبارات بث أو دفع أو سحب أو استرداد عبر مزود؛ وحداتها التشغيلية
  تخص مراحل لاحقة. اختبارات القيد العكسي ضمن تكامل الدفتر فقط.

تعذر الوصول إلى الشبكة وDocker في المحاولات الأولى بتاريخ 2026-11-05؛ أزيل
هذا العائق في جلسة التحقق الحالية. لم يعد نقص الصلاحيات سببًا مانعًا لتثبيت
الحزم أو تشغيل PostgreSQL وRedis. وجود lockfile يثبت حل التبعيات؛ نجاح
تنفيذ CI على GitHub نفسه غير مدّعى هنا.

## إعادة تحقق أساس المرحلة الأولى على جهاز صالح للتشغيل

من جذر المشروع، مع Node 22.13+ أو 24 وDocker Compose:

```sh
cp .env.example .env
source scripts/env.sh
npm ci
docker compose up -d postgres redis
npm run db:validate
npm run db:generate
npm run db:migrate
npm run db:seed
npm run db:seed  # يتحقق من قابلية إعادة التهيئة دون تكرار
npm run check
npm run start:api
```

في طرفية ثانية اختبر `/api/v1/health/live` و`/api/v1/health/ready` وOpenAPI.
عند إيقاف Redis يجب أن تعيد readiness حالة 503، وتظل liveness متاحة.
أعد الخدمة ثم تحقق من تعافي readiness. أعد تطبيق migrate deploy للتأكد
من عدم وجود ترحيلات معلقة. افحص diff بين schema وقاعدة البيانات بأدوات
Prisma، مع توقع اختلافات SQL المضافة يدويًا مثل CHECK وtriggers؛ لا تعالجها
بتشغيل db push الذي قد يفقد هذه الحماية.

اختبارات الكتابة تحتاج قاعدة منفصلة. لا تستخدم قاعدة التطوير ذات البيانات
المهمة ولا قاعدة إنتاج. يمكن إنشاء بيئة محلية منفصلة بالملف المرفق:

```sh
# في طرفية اختبار مستقلة؛ هذه المتغيرات محلية ومخصصة للاختبار فقط.
set -a
source .env.test.example
set +a
docker compose -p livestar-test --env-file .env.test.example up -d postgres redis
npm run db:migrate
npm run db:seed
npm run db:test
docker compose -p livestar-test --env-file .env.test.example down
```

الاختبارات ترفض قاعدة اسمها لا يحتوي `test` افتراضيًا، وتضيف fixtures
معلّمة داخلها. لا تحذف سجل الأستاذ بعد الاختبار لأنه append-only؛ القاعدة
المعزولة قابلة لإعادة الإنشاء. يمكن إبقاء volume الاختبار لإعادة تشغيل
الاختبارات التي تستخدم معرفات فريدة. CI ينشئ الخدمات وقاعدة اختبار منفصلة.

نتائج مطابقة المخطط والبناء واختبارات HTTP والتكامل والترحيلات وإعادة التهيئة
وصلاحيات التطبيق تثبت قبول الأساس البرمجي للمرحلة الأولى. يظل قبول صورة Docker
والنشر منفصلًا ومعلقًا حتى تشغيل الصورة فعليًا. تقدم المراحل التالية موثق في
[سجل التقدم](PROGRESS.md).
