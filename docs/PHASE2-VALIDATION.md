# قبول المرحلة الثانية — المصادقة وإدارة المستخدمين

التاريخ: 2026-11-07. **اجتاز أساس المرحلة الثانية اختبارات القبول الفعلية.**
يشمل ذلك التسجيل والدخول والجلسات والتحقق من البريد والاستعادة والملف الشخصي
والبحث وتصدير الهوية وطلب الحذف. بدأ العمل على واجهات المرحلة الثالثة؛
هذا القبول لا يثبت اكتمال الويب أو Flutter أو البث أو الخدمات المالية.

## النتائج المنفذة

| الفحص | النتيجة | ما يثبته |
| --- | --- | --- |
| `npm run check` | نجح | Prisma validate/generate، بناء TypeScript وفحص الأنواع واختبارات مساحات العمل |
| اختبارات API | 34 اختبارًا ناجحًا | عقود HTTP، Origin وcookies، التحقق من المدخلات، صلاحيات المستخدم، الملفات والبحث والتصدير وفحوص الاعتمادات |
| اختبارات الحسابات | 17 اختبارًا ناجحًا | استمرار صحة الحسابات الدقيقة والتقريب والتقسيم والإسناد |
| `npm run db:test` | 24 اختبارًا ناجحًا على PostgreSQL | اختبارات الدفتر السابقة مع 6 اختبارات للمصادقة والصلاحيات والجلسات والتحديات واحتفاظ مراجع الحذف |
| `npm run db:check-static` | 9 فحوص ناجحة | سلامة المخطط والترحيلات وفصل مخطط المرحلة الأولى المرجعي عن الإضافات الجديدة |
| Prisma migrate diff | نجح؛ `No difference detected` | لا اختلاف بنيوي يكتشفه Prisma بين قاعدة البيانات المهاجرة والمخطط |
| `npm run test:auth:integration` | اختبار دورة هوية كامل ناجح، وأعيد تشغيله مرتين بنجاح | خادم API مبني، ودور قاعدة بيانات محدود، وPostgreSQL وRedis وSMTP فعلي عبر Mailpit |

اختبار الدورة الفعلية سجل حسابًا مع دور USER فقط، وأثبت وصول رسالة التحقق
إلى Mailpit واستهلاك رابطها مرة واحدة، وتدوير refresh على الموبايل ورفض
إعادة الاستخدام مع إلغاء العائلة، وتحديث الملف والتصدير، ثم استعادة كلمة
المرور وإبطال الجلسات القديمة وطلب الحذف وفقد الوصول. لم تُرسل رسائل إلى
مزود خارجي، ولم تُنشأ دفعات أو أرصدة أو معاملات مالية.

العقود الكاملة وأمثلة JSON في [دليل API](../apps/api/README.md)، وتوصف
المسارات المنفذة في `/api/docs` و`/api/openapi.json`. جميع المسارات التالية
تحت `/api/v1`:

| العملية | المسار والسلوك |
| --- | --- |
| التسجيل والدخول على web | `POST /auth/register` و`POST /auth/login`؛ يتطلبان Origin مسموحًا |
| جلسة web | `POST /auth/refresh` يستخدم cookie؛ و`POST /auth/logout` يستخدم Bearer مع Origin |
| جلسة native | `/auth/mobile/register` و`/auth/mobile/login` و`/auth/mobile/refresh` و`/auth/mobile/logout`؛ نقل صريح للتوكن، لا cookie محيط |
| الهوية الحالية | `GET /auth/me`؛ المستخدم والجلسة والصلاحيات الحالية |
| البريد والاستعادة | `POST /auth/email/verify` و`/auth/email/resend` و`/auth/password/forgot` و`/auth/password/reset` |
| الملف الخاص | `GET/PATCH /users/me`؛ يحدّث الاسم والوصف واللغة والمنطقة الزمنية فقط |
| الملف والبحث العام | `GET /users/:username` و`GET /users?query=star&limit=20`؛ حقول عامة لحسابات نشطة، دون بريد أو أسرار |
| تصدير الهوية | `GET /users/me/export`؛ يتطلب Bearer ويصدر مجال الهوية الحالي فقط |
| طلب الحذف | `DELETE /users/me` مع تأكيد كلمة المرور؛ يعيد 202 ويلغي الوصول |

## الجلسات والخصوصية

التسجيل يقبل تاريخ ميلاد مصرحًا به لعمر 18 سنة أو أكثر، وموافقة على النسختين
الحاليتين من الشروط والخصوصية (`2026-11-07`). هذا إقرار ذاتي؛ لا يملأ
`ageVerifiedAt` ولا يعادل KYC أو التحقق القانوني لكل بلد. يمنح الخادم USER
فقط، ويرفض حقول الأدوار أو الامتيازات المحقونة في الطلب.

JWT صالح 15 دقيقة، مع issuer وaudience وsubject ومعرف جلسة. كل طلب محمي
يتحقق من نشاط الجلسة والحساب ويقرأ الأدوار والصلاحيات الحالية. refresh عشوائي
بطول 256 بت، لا يحفظ إلا SHA-256 له، ويتدوّر ذريًا تحت قفل الصفوف. تبقى
نهاية عائلته المطلقة 30 يومًا؛ إعادة استخدام سابق تلغي العائلة قبل رد 401.
يجب أن يسلسل العميل عمليات refresh المتزامنة.

في web يبقى refresh داخل cookie باسم `livestar_refresh`، مع HttpOnly
وSameSite Strict والمسار `/api/v1/auth` وSecure في الإنتاج. الاستجابة JSON
تحمل access token فقط. نقل mobile الصريح يعيد refresh في JSON للتخزين
الآمن على الجهاز. العمليات الحساسة للـcookie تشترط Origin مطابقًا لـ`WEB_ORIGIN`.

روابط البريد عشوائية وحيدة الاستعمال وصالحة 30 دقيقة؛ توضع في fragment
مثل `/reset-password#token=...`، وتخزن مجزأة في قاعدة البيانات. المرحلة
الثالثة تقرأ fragment وتحذفه من سجل المتصفح بعد التقاطه. إعادة ضبط كلمة
المرور تلغي جميع الجلسات الحالية. لا ترجع API أسرار الاستعادة أو تجزئاتها.

التصدير الحالي نطاقه `identity-profile-and-follows`: الحساب والملف والموافقات
والمتابعون والمتابعات، دون تجزئات كلمات المرور أو الجلسات أو التحديات.
لا يشمل بعد تصديرًا شاملًا للمال أو البث؛ يضاف ذلك مع وحداتهما.

طلب الحذف يمحو بيانات الهوية المباشرة من الحساب والملف عبر تمويهها، ويلغي
كلمات المرور والجلسات والتحديات، ويضع الحالة `DELETION_PENDING`. تبقى
الموافقات والمراجع الثابتة للدفتر والسجلات وفق الاحتفاظ المطلوب؛ لا يمثل
الرد حذفًا ماديًا فوريًا لكل السجلات. مدد الاحتفاظ والإنهاء النهائي تحتاج
سياسة تشغيل معتمدة قبل الإطلاق.

## إعادة الاختبارات محليًا

من جذر المشروع، على قاعدة اختبار منفصلة وبقيم الملف المخصص للاختبار:

```sh
set -a
source .env.test.example
set +a
npm ci
npm run db:generate
docker compose -p livestar-test --env-file .env.test.example --profile mail up -d postgres redis mailpit
npm run db:deploy
npm run check
npm run db:test
npm run db:check-static
npm run test:auth:integration
```

اختبار HTTP يشغل عملية API مؤقتة على المنفذ 4002 افتراضيًا ويوقفها عند
الانتهاء. يمكن تخصيص `AUTH_TEST_PORT` و`MAILPIT_TEST_URL` عند الحاجة.
Mailpit يستقبل SMTP على 1025 ويعرض الرسائل على `http://localhost:8025`.
الـfixtures تضاف إلى قاعدة الاختبار فقط؛ لا توجه هذه الأوامر إلى بيانات إنتاج.

## حدود التشغيل المتبقية

- Rate limiting حاليًا داخل كل عملية API. يلزم حد مشترك عبر Redis قبل تشغيل
  نسخ متعددة؛ وجود Redis لفحص الجاهزية لا يعني أن المحدد موزع.
- إرسال SMTP في هذه المرحلة best-effort؛ فشل الإرسال لا يحذف الحساب، ويمكن
  إعادة طلب الرابط. لا يوجد بعد طابور بريد دائم أو إعادة محاولة خلفية.
  `emailDelivery: sent` يعني قبول SMTP؛ الاختبار المحلي أثبت الالتقاط في Mailpit،
  وليس التسليم إلى صندوق بريد خارجي.
- الإنتاج يحتاج SMTP فعليًا مع TLS وإعدادات المرسل، وHTTPS، وقيم `WEB_ORIGIN`
  و`APP_PUBLIC_URL` صحيحة، ومفتاح JWT عشوائيًا فريدًا لا يقل عن 32 بايت.
  قيم `.env.example` و`.env.test.example` محلية ولا تعتمد للإنتاج.
- نصوص الشروط والخصوصية والاحتفاظ، ومصفوفة متطلبات السن والبلدان، تحتاج
  مراجعة المنتج والبلدان قبل الإطلاق. تسجيل نسخة الموافقة لا ينجز تلك المتطلبات.
- لم يثبت تشغيل صورة API النهائية داخل Docker بعد. عولج ضغط مساحة VFS
  محليًا مع إبقاء بيانات PostgreSQL؛ ستعاد محاولة البناء مع حزم الواجهة.
  يظل Compose في المصدر يستخدم صور PostgreSQL وRedis الرسمية.

في تشغيل Docker تشغّل خدمة `migrate` الأمر `db:deploy` الذي يطبق الترحيلات
ويهيئ دور USER والبيانات المرجعية تلقائيًا. بقي Prisma و`tsx` كتبعيات إنتاج
لحزمة قاعدة البيانات كي لا تحذفهما `npm prune --omit=dev` من صورة التشغيل
المشتركة. نجاح بناء الصورة وتشغيل هذا المسار سيُوثق عند التحقق منه فعليًا.
