# نشر LiveStar بخطط مجانية

هذه خطة **نسخة تجريبية عامة** بميزانية شهرية صفر. نجح بناء صورة Docker
المجمعة واختبار تشغيل محلي لتطبيق الإنتاج، لكن لم يحدث نشر عام على الخدمات.
المستودع المحدد هو [dulyd67-arch/new_liev](https://github.com/dulyd67-arch/new_liev)،
وهو مستودع عام متاح للاتصال الحالي. حسابا Render وNeon غير مربوطين حاليًا.
لم تُجهّز مفاتيح مشروع LiveKit Cloud بعد. إنشاء حسابات الخدمات وربطها وتوفير
مفاتيح خادم الوسائط خطوات مطلوبة قبل
تنفيذ النشر؛ وجود `render.yaml` لا يعني أن رابطًا عامًا أُنشئ.

## الخدمات المختارة

| الخدمة | دورها | الحدود التي يجب مراجعتها قبل الإنشاء |
| --- | --- | --- |
| Render Free | حاوية واحدة تشغّل Next.js وNestJS، مع HTTPS ورابط `onrender.com` مجاني | 512MB، وساعات مجانية مشتركة على مستوى الحساب، وتوقف عند الخمول |
| Neon Free | PostgreSQL دائم خارج حاوية التطبيق | تخزين وحوسبة ونقل ضمن حصة مجانية؛ راجع حدود حسابك الحالية |
| LiveKit Cloud Build | نقل الصوت والفيديو عبر WSS وWebRTC مع خدمة الوسائط المُدارة | حصة دقائق المشاركين ونقل البيانات والاتصالات المتزامنة |
| GitHub | حفظ مصدر المشروع ليبني Render منه | يمكن استخدام مستودع خاص؛ لا تحفظ أسرار البيئة فيه |

لا يحتاج هذا المسار إلى دومين مدفوع أو VPS أو فتح منافذ UDP. يستخدم الموقع
العنوان المجاني الذي يعطيه Render، وتستخدم الوسائط عنوان LiveKit Cloud العام.
لا تضف موارد مدفوعة أو قرصًا مدفوعًا أو ترقية تلقائية. حافظ على إعدادات
إنفاق صفر، ولا تضف طريقة دفع إذا أردت توقف الخدمة عند انتهاء الحصة بدل
تحصيل تجاوزات. اختيار `plan: free` وحده لا يضبط سياسة فواتير الحساب كله.

المراجع الرسمية التي روجعت في 2026-11-13:

- [حدود Render المجانية](https://render.com/docs/free): 750 ساعة شهريًا لكل
  مساحة عمل، نوم بعد 15 دقيقة من غياب الطلبات، واستيقاظ قد يستغرق نحو دقيقة.
  لا تستخدم قاعدة Render Postgres المجانية لهذا المشروع لأنها تنتهي بعد 30 يومًا.
- [أسعار LiveKit](https://livekit.io/pricing): خطة Build بلا بطاقة دفع، مع
  5,000 دقيقة اتصال WebRTC و50GB نقل شهريًا و100 اتصال متزامن وفق الصفحة
  التي روجعت. الدقيقة تخص كل مشارك متصل، وليست دقيقة بث واحدة لجميع المشاهدين.
- [أسعار Neon](https://neon.com/pricing): اختر Free وتحقق من حصص حسابك وقت الإنشاء.

قد تتغير الخطط. عند ظهور طلب دفع أو خطة مدفوعة، توقّف وراجع الاختيار بدل
إكمال الاشتراك. هذه الحدود لا تجعل النسخة خدمة غير محدودة أو مضمونة التوفر.

## 1. جهّز الحسابات والمصدر

1. أنشئ حسابات Render وNeon وLiveKit Cloud واختر الخطط المجانية فقط.
2. اربط حسابي Render وNeon لتنفيذ الإعداد من المحادثة، أو اتبع الخطوات أدناه
   مباشرةً في لوحتي الخدمتين. لا ترسل كلمات مرور أو مفاتيح API في المحادثة.
3. استخدم المستودع المحدد أعلاه، وتأكد من وجود المصدر و`render.yaml` في
   جذر فرعه `main` قبل ربط Render. أبقِ `.env` وكل ملفات الأسرار خارج Git؛
   المستودع عام. إذا اخترت لاحقًا مستودعًا خاصًا بديلًا، امنح اتصال GitHub
   وRender صلاحية الوصول إليه.
4. أنشئ مشروع LiveKit Cloud بخطة Build. عنوانه العام يبدأ بـ`wss://`.
   احفظ المفتاح والسر في إعدادات البيئة لدى Render، وليس في ملفات الواجهة.

التحقق الحالي أكد اتصال تطبيق GitHub وصلاحية الكتابة إلى المستودع العام
`new_liev`. حسابا Render وNeon غير مربوطين، ومفاتيح مشروع LiveKit Cloud
غير متوفرة بعد. لا يمكن لهذه الملفات إنشاء الحسابات أو الموافقة على شروط
الخدمات نيابةً عنك.

## 2. أنشئ قاعدة Neon والدور المحدود قبل الترحيلات

أنشئ مشروع Neon Free وقاعدة PostgreSQL. يلزم اتصالان لنفس قاعدة البيانات:

- `DATABASE_MIGRATION_URL`: الاتصال المباشر بمالك المخطط، لتطبيق الترحيلات.
- `DATABASE_URL`: اتصال المستخدم المحدود **`livestar_app`** الذي يستعمله API.

أنشئ دور `livestar_app` في قاعدة Neon **قبل أول نشر**. يمكن للأداة المتصلة
تنفيذه، أو ينفذه المالك من SQL Editor مع كلمة مرور قوية مُولّدة محليًا.
لا تستخدم كلمة المرور الواردة في مثال تطوير ولا تطبعها في المحادثة. ضع
كلمة مرور الدور في رابط الاتصال داخل إعدادات Render مع تشفير أحرف URL.
استخدم `sslmode=require` كما في اتصال Neon، واختر رابط المالك المباشر
للترحيل ورابط الدور المحدود المناسب للتطبيق؛ يمكن أن يكون الأخير pooled.

السبب في هذا الترتيب أن الترحيلات تمنح صلاحيات `livestar_app` فقط إذا كان
الدور موجودًا عند تطبيقها. إنشاء الدور بعد الترحيلات ثم إعادة تشغيل التطبيق
لا يعيد تنفيذ الترحيلات القديمة ولا يصلح الصلاحيات تلقائيًا. لا تعالج ذلك
بحذف قاعدة تحتوي بيانات أو بإعطاء التطبيق سر المالك كاتصاله المعتاد.

## 3. أنشئ خدمة Render من Blueprint

في Render اختر Blueprint واربط المستودع الذي يحتوي `render.yaml` في جذره.
راجِع أن المورد الوحيد هو Web Service بخطة **Free**. لا ينشئ الملف قاعدة
Render مدفوعة أو مجانية مؤقتة، ولا Redis ولا قرصًا دائمًا.

أدخل المتغيرات الخمسة المطلوبة من إعدادات الخدمات:

| المتغير | المصدر |
| --- | --- |
| `DATABASE_URL` | اتصال Neon بالدور `livestar_app` |
| `DATABASE_MIGRATION_URL` | اتصال Neon المباشر بمالك المخطط |
| `LIVEKIT_URL` | عنوان مشروع LiveKit Cloud العام `wss://...` |
| `LIVEKIT_API_KEY` | مفتاح مشروع LiveKit Cloud |
| `LIVEKIT_API_SECRET` | سر المشروع، ويحفظ كسر في إعدادات Render |

ينشئ Render قيمة JWT عشوائية عبر `generateValue`. يحتفظ بها بين عمليات النشر؛
تغييرها يبطل رموز الدخول الحالية. لا تستبدلها بمفتاح التطوير المرفق.

لا يلزم إدخال اسم نطاق يدويًا: يقرأ مشغّل التطبيق العنوان الموثق
`RENDER_EXTERNAL_URL` ويضبط أصل الموقع والمصادقة منه. إذا أدخلت
`APP_PUBLIC_URL` يدويًا فيجب أن يكون أصل HTTPS عامًا مطابقًا للموقع.
مرجع Render: [متغيرات البيئة الافتراضية](https://render.com/docs/environment-variables).

## 4. كيف تعمل الحاوية

يبني `infra/docker/free.Dockerfile` الواجهة والخادم مع عنوان API داخلي ثابت
`http://127.0.0.1:4001/api/v1`. قواعد تمرير Next.js تُثبّت وقت البناء؛
تغيير العنوان الداخلي يتطلب إعادة بناء متوافقة، وليس تغيير قيمة وقت التشغيل فقط.

يتحقق `scripts/start-free.mjs` من إعداد الإنتاج قبل تشغيل الترحيلات والتهيئة
المرجعية، ثم يتحقق من جاهزية API الخاص على `127.0.0.1:4001`، ثم يشغّل Next.js على `0.0.0.0:$PORT`
العام الذي يحدده Render. فحص Render هو `/api/v1/health/ready` عبر الواجهة.
توقف أي من الخادمين يوقف الخدمة كلها بدل ترك واجهة تبدو سليمة وخلفيتها ميتة.

تُزال قيمة اتصال المالك من بيئة العمليتين بعد الترحيل، وتُزال أسرار API
المعروفة من بيئة Next.js أيضًا. هذا تقليل للتعرض، وليس عزلًا أمنيًا كاملًا
بين عمليات تعمل في الحاوية وتحت المستخدم نفسه. لا تنشئ ملفات أسرار داخل الصورة.

## 5. قيود النسخة الصفرية

- Redis معطّل صراحةً بـ`REDIS_OPTIONAL=true`؛ فحص الجاهزية يعرض `disabled`
  بدل ادعاء اتصال غير موجود. بيانات الحسابات والمحادثة تبقى في PostgreSQL.
- البريد معطّل صراحةً بـ`EMAIL_ENABLED=false`؛ منافذ SMTP الشائعة 25 و465
  و587 محجوبة في Render Free. التسجيل والدخول والبث تعمل، لكن إرسال روابط
  تأكيد البريد والاستعادة يحتاج خدمة بريد مناسبة لاحقًا. لا تدّعي الواجهة
  أو API أن رسالة أُرسلت حين تكون الخدمة معطّلة.
- الذاكرة محدودة: افتراضياً طلب اشتقاق كلمة مرور واحد متزامن، وحدّ V8 لكل
  عملية 128MB. scrypt وPrisma يستخدمان ذاكرة أصلية خارج هذا الحد؛ يلزم قياس
  الاستخدام الفعلي، وقد يعيد المضيف تشغيل الخدمة عند ضغط الذاكرة.
- خمول Render وانتهاء حصص LiveKit أو Neon قد يوقفان النسخة. لا تضف طلبات
  مصطنعة لإبقاء الاستضافة مستيقظة أو تتجاوز قيود الخطط المجانية.

## 6. نتائج التحقق المحلي وحدودها

نجح **73 اختبارًا للخادم**، و**4 اختبارات لمشغّل النشر المجاني**، و**4 تحققات
للواجهة بالمتصفح**.

نجح بناء الصورة، ونجح اختبار تشغيل من **تسعة تحققات**: جاهزية PostgreSQL
مع تعطيل Redis، عرض HTML عبر Next.js، الإبلاغ الصحيح عن تعطيل البريد، حجب
Swagger العام، عدم إتاحة استعادة كلمة المرور بلا بريد، إنشاء حساب وملف تعريف
ارتباط تجديد آمن، الدخول باستخدام scrypt، قراءة الملف الشخصي بعد المصادقة،
وتسجيل الخروج.

شُغّلت ملفات تطبيق الإنتاج بربط للقراءة فقط داخل نفس أساس Node.js 22 Alpine،
مع قاعدة اختبار محلية معزولة ومفاتيح LiveKit Cloud اختبارية غير صالحة.
هذا الاختبار لا يثبت نشرًا عامًا أو اتصالًا حقيقيًا بخدمة الوسائط السحابية.

رُصدت ذروة **445.5MiB** من مجموع RSS لعمليات حاوية التطبيق خلال 8 ثوانٍ
من التسجيل والدخول، بعينات كل 25ms. يعمل Docker هنا دون cgroups، ولذلك
لم يُفرض حد 512MiB المطلوب. هذه ملاحظة محدودة، وليست اختبار ضغط أو نجاحًا
تحت حد ذاكرة مفروض؛ يجب إعادة القياس على Render مع حمل مناسب قبل فتح
النسخة لجمهور واسع.

بعد تحديثات NestJS وNodemailer، بقيت **أربع نتائج `high`** في تدقيق npm
ضمن اعتماديات Prisma CLI المستخدمة في تهيئة قاعدة البيانات عند الإقلاع.
هذه نتائج معروفة متبقية؛ لا تُعامل الحزمة باعتبارها خالية من الثغرات.
لم يُستخدم `npm audit fix --force` للانتقال إلى Prisma 7 لأن ذلك يحتاج ترقية
متوافقة واختبارات مستقلة، ولا يُعد إصلاحًا آمنًا تلقائيًا.

## 7. تحقق من النشر قبل دعوة المستخدمين

1. يجب أن تنتهي عملية البناء والترحيل دون خطأ ويعيد فحص الجاهزية `200`.
2. افتح الرابط العام عبر HTTPS واختبر التسجيل والدخول وتجديد الجلسة.
3. ابدأ بثًا من جهاز، وشاهده من جهاز آخر على شبكة مختلفة؛ تحقق من الفيديو
   والصوت والمحادثة وإنهاء البث. تحميل الصفحة وحده لا يثبت وصول الوسائط.
4. راقب الذاكرة وحصص البيانات والدقائق في لوحات الخدمات، وتحقق من توقف
   الخدمات عند الحدود بدل الفوترة.

تعريف الحاوية وملفات النشر لا يثبتان أن حسابات الخدمات اتصلت أو أن التطبيق
نُشر. يسجل المنفذ نتائج البناء والتشغيل الفعلية عند توفر الاتصال والمفاتيح.
